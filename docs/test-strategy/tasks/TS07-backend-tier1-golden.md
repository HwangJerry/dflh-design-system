# TS07 — Backend: Tier 1 golden API responses from the real router on the production baseline schema

Repo: dflh-saf-v2 (work in backend/). Branch: `test/ts07-tier1-golden`.

Goal (PLAN D1/L3): produce normalized golden JSON files of real responses for the Tier 1 mobile flows, generated by the
real HTTP stack (router → middleware → handler → service → repository → MariaDB), so iOS/Android can later decode them with
their real DTOs (TS08). These tests also act as the first HTTP-level integration tests (L4).

Building blocks already on main:
- internal/testsupport/mariadb: `mariadb.Start(t).NewDatabase(t, mariadb.ProdBaseline(t)...)` gives a fresh DB with the exact
  production schema (migrations 001-077 recorded). Docker-gated by DFLH_DOCKER_TESTS=1; skip otherwise. Needs TestMain with
  `os.Exit(mariadb.Run(m))` in the test package.
- internal/testsupport/golden: `golden.Assert(t, name, body, volatileKeys...)`, `GOLDEN_UPDATE=1` to write.
- cmd/server: `wireDeps(db, cfg, logger)` (wire.go:48) and `registerRoutes(...)` (routes.go:80) are the real constructors. Tests
  in `package main` (cmd/server) can call them directly — do NOT move them in this task.

Do:
1. In cmd/server add an integration test file (Docker-gated) with a helper that builds the full router against the baseline DB
   using a test config built via config loading from env with safe values: no SMS provider (messages dropped), review test
   number + fixed code for OTP (use SMS_REVIEW_TEST_PHONES / SMS_REVIEW_TEST_CODE; pick 01000000001 / 123456 — synthetic),
   PUSH_ENABLED=false, PG_AUDIT_LOG_PATH and UPLOAD_BASE_PATH under t.TempDir(), account-erasure readiness satisfied with
   synthetic values under t.TempDir() or disabled if that keeps startup valid (explain), JWT secrets synthetic, fresh in-memory
   cache per test. Serve with httptest.NewServer. Never read real env files.
2. Seed only synthetic data (a test alumni roster/member rows as the flows need; use SQL statements in the test).
3. Golden cases (each writes testdata/golden/<name>.json under cmd/server; list volatile keys explicitly):
   - settings_public: GET /api/settings/public (include app_update_policy_ios/android keys as returned)
   - check_id_available / check_phone_taken: GET /api/auth/check-id, /api/auth/check-phone
   - phone_verification_request / phone_verification_confirm: POST /api/auth/phone/verification/{request,confirm} with the test number
   - register_success: POST /api/auth/register (native ID signup, with the verification token and consent version the server requires)
   - mobile_login_success and mobile_login_invalid_password: POST /api/auth/mobile/login (the endpoint the apps use; check both apps'
     API code to confirm paths/bodies/headers they send, and send the same shape)
   - refresh_success: POST /api/auth/refresh
   - auth_me: GET /api/auth/me with the access token (approved member)
   - app_update_required_426: any authenticated request with X-App-Platform/X-App-Build below a force policy you set in app_settings
   - account_deletion_request: POST /api/auth/account/deletion-requests for a disposable member (then GET /api/account-deletion/receipt if
     the app uses it)
   - error envelope examples already covered above (401/409/426) are enough; do not add more.
   For each case also assert status code and the key business facts (not just the golden), e.g. register creates a pending member,
   the phone claim row exists, refresh rotates the token.
4. Add a short README section (backend/internal/testsupport/README.md or cmd/server) listing the golden files and how to regenerate
   (`DFLH_DOCKER_TESTS=1 GOLDEN_UPDATE=1 go test ./cmd/server -run Golden`). Generated files are committed.
5. If a flow cannot run on the baseline schema or needs production code changes to be testable, stop that case, keep the others,
   and explain precisely in the report (do not change production code beyond trivial, clearly-safe test seams; list any).

Verify: `go vet ./...`; `go test ./...` (Docker off: new tests skip); `DFLH_DOCKER_TESTS=1 go test ./cmd/server -run Golden -count=1 -v`
(all pass, run twice to prove goldens are stable); `bash scripts/test-coverage.sh` with DFLH_DOCKER_TESTS=1 and report handler/service
coverage change. Commit (goldens included).
