# Android 로컬 우선 로그아웃 구현 결과

2026-10-10. 구현 브랜치: `fix/auth-local-first-logout-20261010`, 기준 커밋 `00b8f26`. 수정은 현재 작업 브랜치의 변경 파일에 있다. 수정 release APK를 갤럭시에 설치해 검수했으며 Play 배포는 수행하지 않았다.

**Android 코드 보완, 전체 단위 테스트 685개, debug/release 빌드, Kakao R8 검사와 갤럭시 검수를 완료했다.** 실행 권한 복구 후 아래에 적었던 빌드·ADB 제한을 해소했다. 상세 실기기 결과는 [기기 QA 보고서](android-local-first-logout-device-2026-10-10.md)에 기록한다.

## 구현

- `MainActivity`의 푸시 해제 선행 콜백을 제거했다. 내정보와 승인/복원 화면 등의 기존 로그아웃 요청은 `SessionViewModel.signOut`을 통해 동일한 로컬 우선 경로를 사용한다.
- ViewModel은 네트워크 작업을 예약하기 전에 동기적으로 로컬 로그아웃을 수행한다. Repository가 원래 세션과 푸시 토큰을 캡처하고, 기존 암호화 저장소의 동일 커밋에 재시도 정보 저장과 활성 로그인 삭제를 넣는다.
- 기기 인증 정보와 메모리 상태를 종료한 뒤 앱 범위의 CoroutineScope에서 서버 정리를 실행한다. 인증 화면이나 ViewModel이 종료되어도 정상적인 앱 범위 정리는 계속된다. 프로세스 종료 후에는 저장된 재시도 기록을 사용한다.
- `AuthApi`는 원래 Refresh 증명 및 선택적인 기기 토큰으로 기존 `auth/logout/deferred`를 호출한다. 현재 로그인 헤더, 토큰 refresh, 자동 401 재시도를 사용하지 않는다. 204와 정확한 `X-Session-Logout-Result: confirmed`를 함께 확인한 경우만 종료 확인으로 판정한다.
- Access 전용 기존 세션은 캡처한 Bearer로 `auth/logout`을 사용한다. 빈 204 응답도 정상 처리한다. Refresh 증명 기반과 Access 전용 경로는 실제 서버 계약에 따라 구분한다.
- 재시도 항목에 선택적 기기 토큰을 추가했다. 기존 저장 키와 v1 항목은 유지하고, 필드가 없는 기존 JSON도 읽을 수 있다. 재시작·재시도 중 현재 로그인 또는 현재 기기의 다른 회원 정보를 끌어다 사용하지 않는다.
- 늦은 미확인 결과와 저장 오류 안내는 해당 로그아웃의 generation/revision에만 적용한다. 다른 계정뿐 아니라 같은 회원의 새 로그인도 보존한다.
- 저장 실패 시 이전 토큰은 이 프로세스에서 재사용하지 않으며 안전한 저장을 확인하지 못했다는 안내를 표시한다. 저장 실패를 프로세스 재시작까지 안전한 로그아웃으로 주장하지 않는다. 저장된 로그인과 남은 정리 요청이 일치하면 부팅 복원도 차단한다.

iOS와 서버의 제품 코드는 변경하지 않았다. 새 migration은 추가하지 않았다. Android 인증·네트워크·푸시 동작 문서를 실제 구현에 맞췄다.

## RED → GREEN 근거

현재 수정 전 화면 콜백을 실제 소스에서 추출하고 푸시 응답을 보류했을 때, 로컬 로그인 삭제가 네트워크 완료 전에 끝나야 한다는 검증이 실패했다. 원래 API 구현에서도 종료 증명 경로를 사용해야 한다는 새 테스트가 기존 Bearer 로그아웃 요청을 관찰해 실패했다. 각각 `android-callback-result.txt`, `red-junit.log`에 남겼다.

수정 후 실제 ViewModel의 로그아웃 진입점은 스케줄러를 진행하기 전부터 로그인 정보를 지우고 SignedOut을 발행한다. 보류된 네트워크 정리는 앱 범위에서 유지된다. 추가 회귀 테스트는 아래 상황을 검증한다.

| 상황 | 로컬 테스트 결과 |
| --- | --- |
| 서버 정리가 멈춘 상태의 UI 로그아웃 | 로그인 정보 즉시 삭제·SignedOut, ViewModel 종료 후 정리 계속 |
| A 로그아웃 후 B 또는 같은 A로 재로그인 | 늦은 미확인 결과가 새 로그인과 화면 상태를 유지 |
| 오프라인 로그아웃·재시작·온라인 복구 | 정리 기록만 복원하고 원래 기기 토큰으로 재시도 |
| 저장된 로그인과 정리 요청이 함께 남은 재시작 | 기존 로그인 복원 차단 |
| 반복 로그아웃·기기 토큰 변경 | 원래 정리 정보 보존, 불필요한 성공 요청 중복 방지 |
| 기기 토큰 삭제/정리 기록 저장 실패 | 메모리 토큰 차단, 영속화 경고 표시 |
| 원래 증명·Access 전용·401·누락/잘못된 확인 헤더 | 현재 인증/Refresh 없이 정리, 확인된 종료와 미확인 구분 |
| 기존 v1 기록 및 Refresh 만료 경계 | 저장 호환성과 원래 만료 상한 유지 |

## 실행한 검증

- 수정 전 푸시 응답 보류와 잘못된 종료 API 호출을 RED로 확인한 뒤 수정 소스로 인증 JVM 테스트 **149개**가 통과했다.
- 권한 복구 후 정식 Gradle 작업 `:app:testDebugUnitTest :app:assembleDebug :app:assembleRelease`가 성공했다. **94개 suite, 단위 테스트 685개, 실패·오류·건너뜀 0개**다. 이전 직접 JVM 실행/186개 Kotlin 컴파일보다 넓은 정식 빌드 결과다.
- Minified release APK의 Kakao R8 검사도 통과했다: `checkAccessToken`의 `Call<AccessTokenInfo>` 시그니처 유지.
- 서버 계약 테스트 **58개 통과 / 실패·건너뜀 0개**. 운영에서는 migration 085의 세션별 푸시 소유권 컬럼과 실제 deferred logout 응답을 별도로 확인했다.
- 갤럭시에서 수정 release의 ID/PW·카카오 정상/오프라인 로그아웃, 자동 로그인, 강제 종료 후 상태 유지와 재연결 시 서버 정리를 검수했다. 같은 QA 회원의 별도 세션과 root 관리자 세션 보존도 확인했다.
- 같은 수정 소스의 별도 debug APK와 로컬 제어 서버로 지연 응답·정리 중 강제 종료·A 로그아웃 후 B 로그인 경합을 실기기에서 검수했다. 운영 서버를 지연시키거나 운영 계정 B를 추가하지 않았다.

## 적용과 남은 범위

Android QA 회원 12827(`AndroidLogout2610`)을 가입·인증 신청했고 사용자가 관리자 승인을 완료했다. ID/PW 비밀번호는 새 QA용 임의 값으로 생성했으며 기존 실제 사용/root 비밀번호를 읽거나 사용하지 않았다. Android의 카카오 계정을 이 QA 회원에 연결했다. 회원가입 신청 자체는 빌드 준비 중 기존 설치 APK로 수행했으므로 이를 수정 APK의 신규 가입 전체 회귀 통과로 주장하지 않는다.

임시 SMS 테스트 전화번호 설정은 원래 값으로 복구했다. root 회원 12813과 iOS 소셜 계정은 변경하지 않았다. 새 서버 migration, 서버 제품 코드 배포, Play 배포는 수행하지 않았다.

이번 변경의 Android 로그아웃 완료 조건을 실기기에서 확인했다. **iOS 신규 회귀, 실제 푸시 알림 전달, Android 탈퇴 요청 24·25·26의 보존기간 이후 최종 삭제**는 별도 후속 항목이다. 운영 Access 만료·동시 Refresh 등의 시간 경계와 저장 실패는 코드/서버 계약 테스트로 검증했으며 모든 경계를 실기기에서 재현했다고 주장하지 않는다. 정기 결제는 범위에서 제외했다.
