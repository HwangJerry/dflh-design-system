# iOS 인증 실기기 재검수 — 2026-10-11

최초 검수 앱에서 **확정 결함 1건(IOS-AUTH-01)**을 발견했다. 이후 [비밀번호 오답·세션 만료 구분 보완](ios-password-error-remediation-2026-10-11.md)을 구현하고 수정 앱의 동일 iPhone 회귀를 통과해 해당 결함의 해결을 확인했다. 전체 인증 검수의 미검수 범위는 남아 있다. 최신 앱에서 ID/PW 신규 가입·승인 대기·승인 후 자동 로그인·정상 로그아웃, 카카오와 Apple의 가입 취소·연결·해제·재연결, 서버 세션 종료 감지, 오프라인 자동 로그인 정보 보존과 온라인 복구를 확인했다. 가입 제출·탈퇴와 추가 경계 검사는 아래 표에서 구분한다. 이전 검수 결과를 이번 최신 앱의 새 통과로 합산하지 않는다.

## 최초 확정 결함: IOS-AUTH-01 / P2 — 후속 수정·실기기 회귀 완료

**잘못된 현재 비밀번호를 한 번 제출하면 iOS의 로그인이 풀린다. 서버의 로그인 세션과 푸시 등록은 남는다.**

승인된 QA12830의 정상 로그인과 자동 복원을 먼저 확인했다. 16:20:09 KST에 잘못된 현재 비밀번호를 한 번 제출하자 다음 초에 로그인 시작 화면으로 이동했다. 오류 안내는 확인되지 않았다. 실제 화면과 AX 상태, ‘잘못된 현재 비밀번호는 기존 로그인을 유지해야 한다’는 단언이 함께 실패했다. `WrongCurrentPassword`는 1개 검사/18.045초 FAIL이며 자동화 선택자 오류와 구분되는 제품 결함이다.

서버 요청은 다음 순서였다.

1. `POST /api/profile/password` → 401
2. `POST /api/auth/refresh` → 200
3. `POST /api/profile/password` → 401

사용자 제출 1회에 비밀번호 변경 요청이 2회, refresh가 1회 발생했다. 16:22:04의 서버 상태에서 원래 QA 세션은 활성이고 푸시 등록도 1개였다. refresh는 정상 회전했지만 비밀번호 갱신 시각은 가입 시각 그대로여서 비밀번호 변경은 없었다. root 세션과 Android QA 상태는 유지됐다.

원인은 `ProfileService`의 기본 재시도 정책과 `APIClient`의 모든 authenticated401에 대한 refresh 처리다. 재요청401에서 로컬 세션을 종료한다. 서버의 `WRONG_PASSWORD`는 현재 비밀번호 입력 오류이므로 다음 계약으로 보완해야 한다.

- 첫 `WRONG_PASSWORD401`은 refresh·재요청 없이 원래 안내를 전달한다.
- 최종401이 같은 오류이면 원래 서버 code/message를 보존하고 로그인 상태를 유지한다.
- 실제 access 만료 → refresh200 → 재요청에서 WRONG_PASSWORD가 발생한 경우에도 갱신된 유효 세션을 유지한다.
- 정상 만료 회복과 실제 invalid refresh의 기존 종료 정책을 보존한다.

`retryNever`만 설정하면 현재 APIClient가 authenticated401을 일반 인증 오류로 치환하므로 안내 복구까지 충족하지 못한다. 제품 수정은 아직 수행하지 않았다. [최소 보완·회귀 설계](../../build/ios-auth-device-audit-20261011/audit/ios-auth-requirement-regression-design.md)에 구체적인 대조 사례를 기록했다.

비밀번호 변경 화면의 오류 매핑도 함께 보완해야 한다. 현재 `ProfileView.swift`는 일반 unauthorized를 비밀번호 오답 안내로 매핑하고 `.server(WRONG_PASSWORD)`는 일반 실패 안내로 처리한다. 명시 WRONG_PASSWORD를 입력 안내로 표시하고 실제 세션 만료를 비밀번호 오답으로 안내하지 않는 대조가 필요하다.

동일한 입력 오류를18:02:21 KST에 Galaxy Note9의 검증 release에서 새로 재검수했다. Android는 password401 1회·refresh0·logout0, 오답 안내·폼·동일 세션을 유지했고 앱 재실행 후에도 동일 회원으로 복원됐다. 현재 검수한 버전의 이 결함은 iOS에서만 재현됐다. [Android 실기기 재검증](android-wrong-current-password-recheck-2026-10-11.md)에 실제 설치 SHA·UI·서버·최종 로그아웃 근거를 구분해 기록했다.

직접 근거는 `WrongCurrentPassword-summary.json`, `wrong-current-device-result.json`, `server/wrong-current-password-{before,after}.txt`, `server/wrong-current-password-window.jsonl`이다. 요청 body/원문 토큰을 읽지 않았으며, 서버 오류 계약과 UI·HTTP 순서·비밀번호 보존을 대조해 판정했다.

### 검수 후 잔여 세션 정리

오류 뒤 정상 Native 로그인으로 새 세션을 만들었을 때 기존 잔여 세션과 함께 2개가 활성인 것을 확인했다. 16:23:54에 앱의 표준 전체 로그아웃을 수행했고 다음 초에 서버204·푸시 해제200을 확인했다. 16:24:27에는 활성 세션/푸시0, refresh 4개 모두 폐기 상태였다. 회원·승인·Native 로그인 수단·전화 소유권·동의·비밀번호는 보존됐다. 이 후속 정리는 결함 자체가 수정됐다는 근거가 아니다.

## 카카오 취소와 강제 종료의 경계

초기 진단은 Talk 앱 우선 실행만 확인하고 callback을 끝까지 관찰하지 못했다. 별도 테스트의 background AX 조회 실패와 동의 버튼 선택자 실패는 하네스 문제로 제외했다. QA와 무관한 AX/화면이 포함된 생성 capture는 폐기했고 기기앱·대화에는 변경하지 않았다.

최신 `KakaoSingleLifecycleFrame`은 SDK 시작부터 제공자 동의·앱 callback·명시 취소·재실행을 하나의 테스트에서 확인했다. 16:27:13 KST mobile202/prefill200 → 16:27:14 cancel204와 16:28:10 신규 회원0·iOS 제공자 소유권0·QA 소셜 identity0·활성 세션/푸시0이 일치한다. 독립 검토자도 같은 자료를 대조했다.

앞선 지연 callback은 16:27:06에 별도의202/prefill200을 만들었고 새 테스트 전에 앱이 강제 종료됐다. 이 이전 가입 continuation의 cancel 요청은 관찰되지 않았다. 서버 continuation은 로그인 세션과 별개이며 토큰별 5분 TTL이다. 새 토큰의 취소와 앱의 로그인 화면 복귀만으로 이전 토큰의 즉시 취소까지 증명할 수 없다.

## 환경과 결과 해석

`ios-device-runner` 및 `gstack-ios-qa` 스킬을 확인했다. 이 앱은 ObservableObject/Xcode project여서 gstack StateServer bootstrap 조건을 충족하지 않는다. DebugBridge를 삽입하지 않고 기존 실제 XCUITest 방식으로 검사했다.

첫 CoreDevice UUID destination은 Xcode hardware UDID와 달라 검사0으로 제외했다. 올바른 destination의 첫 실행도 UI Automation 초기화 전에 실패했다. 사용자에게 잠금 해제·UI 자동화·허용 팝업 확인을 요청했고 최신 앱/새 실행기 재시도에서 복구됐다. 이후 앱 테스트 결과와 초기 환경 실패를 구분했다.

Chrome plugin은 설치·확장·nativehost 확인 및 승인된 새 창 재연결 후에도 `Browser is not available: chrome`를 반환했다. 관리자 DB 쓰기나 인증정보 추출로 우회하지 않았으며 회원12830 승인만 사용자에게 요청했다. 승인 완료는 서버 상태로 확인했다.

과거 QA12820/12826·요청28/29는 completed이고 회원·로그인 수단·전화 소유권·서비스 세션은 삭제된 것을 확인했다. 해당 iOS 테스트 번호는 초기에는 소유자0, Native QA12830 소유를 거쳐 정상 탈퇴로 해제됐고 현재 순수 카카오 QA12831이 소유한다. Apple 순수 신규 가입을 같은 번호로 끝까지 검수하려면 카카오 QA의 정상 탈퇴 완료가 먼저 필요하다. 가입 취소·기존 계정 연결을 가입 완료로 집계하지 않는다.

비공개 실행 근거는 `build/ios-auth-device-audit-20261011/`에 보관한다. 원래 개인 비밀번호·기기 Keychain 토큰·제공자 ID 원문을 조회하지 않았고 보고서에 QA 비밀번호·전화번호·인증코드는 포함하지 않는다.

## 카카오 SDK 자격 증명의 별도 범위

서비스 세션과 카카오 SDK의 앱별 토큰 저장소는 다르다. 양 플랫폼의 공식 SDK는 OAuth 성공 callback 전에 access/refresh token을 지속 저장한다. 현재 앱 소스에는 가입 취소·서비스 인증 실패·표준 로그아웃에서 SDK 저장소를 명시적으로 비우는 호출이 없다. 따라서 서비스 세션0 결과를 SDK token0으로 확대하지 않는다.

이 사실은 앱 소스와 로컬 공식 SDK 구현으로 확인했다. 기기의 SDK 토큰 원문·존재·유효성을 직접 조회하지 않았으므로 실제 기기 잔존/악용 재현으로 확정하지 않는다. 로컬 SDK cache 정리, 앱 OAuth 원격 종료, 서비스 계정 연결 해제, KakaoTalk 자체 로그아웃은 서로 다른 작업이다. Apple의 저장된 provider identifier도 서비스 인증 세션과 구분한다.

[SDK 범위 감사](../../build/ios-auth-device-audit-20261011/audit/provider-sdk-credential-scope.md)에 근거와 추가 회귀안을 기록했다. 정책을 정한 뒤 늦은 이전 인증 작업의 정리가 새 SDK 자격 증명을 삭제하지 않는지까지 대조해야 한다. 이번 QA에서는 SDK 설정·토큰 저장소·KakaoTalk 자체 계정에 변경하지 않았다.

## 오프라인 상태 보존과 온라인 복구

기존 Control Center의 네트워크 선택자는 현재 iOS 화면에서 사용할 수 없었다. Connectivity 접근성 Icon도 유효한 화면 좌표를 주지 않았다. 두 경우 모두 실제 네트워크 변경 전에 중단했으며 제품의 오프라인 인증 실패로 집계하지 않는다. 비행기 모드·VPN·개인용 핫스팟은 조작하지 않았다.

첫 실행기는 차단 중 원격 실행 연결이 끊겨 전체 검사 결과가 실패했다. 이는 호스트 연결 실패이며 앱의 인증 실패로 집계하지 않는다. 네트워크가 복구된 뒤 추가 차단 없이 별도 온라인 복구 검사를 수행했다. 17:20:17 연결 가능 상태를 직접 확인하고 앱을 재실행해 같은 QA12830으로 돌아왔다(6.423초 PASS). 서버 me200·푸시 등록200, 추가 Native 로그인/refresh0, 기존 세션 동일성을 대조했다. 따라서 오프라인 상태 보존과 온라인 복구의 실제 단계별 증거를 확보했지만 첫 검사를 하나의 연속 PASS로 기록하지 않는다.
