## 2. 작업 0 — 기준 및 회귀 테스트 준비

수정 시작 시 각 저장소 HEAD와 미커밋 변경을 기록한다. 계획 작성 시 Android HEAD는 `f2f5996`, backend/web HEAD는 `4dee5fa`이며, 최초 QA 기준과 다르다. Android 설치 앱도 현재 소스와 다르므로 수정 소스로 빌드한 앱에서 최종 재현 검수를 한다.

- 보관한 Android 8개 probe와 backend 재연결 probe를 정식 테스트 구조에 맞게 편입한다. 테스트 fixture를 문서 파일에 의존하지 않도록 정리한다.
- 각 실패를 해당 결함 ID와 연결한다. 이미 수정된 경우 실제 차이와 통과 근거를 기록하고 중복 수정하지 않는다.
- 정상 대조군을 유지한다: 온라인 자동 로그인, refresh rotation, 최초 소셜 연결, 마지막 로그인 수단 해제 방지, 가입 실패 rollback, 승인 대기 권한 제한.
- 기존 E2E의 대기 문구·설정 진입 helper를 현재 UI에 맞춘다. assertion을 완화해 실패를 숨기지 않는다.
- backend 기본 테스트의 migration manifest 3개 실패는 별도 기준선 문제로 추적한다. 승인된 migration 계약과 대조해 해결하며 기대값을 일괄 갱신하지 않는다.

산출물은 결함별 회귀 테스트, 수정 전 결과, 저장소별 기준 커밋이다. 이후 작업마다 관련 테스트와 기존 정상 경로를 함께 실행한다.

## 3. 작업 1 — Android 세션 수명과 응답 순서

대상: `SessionRepository.kt`, `TokenSessionManager.kt`, 필요한 `SessionState`/네트워크 오류 처리 및 로그인·가입 화면.

### 변경 내용

1. **세션 세대와 인증 작업 식별자를 도입한다.** 로그아웃, 탈퇴, 가입 취소, 새 로그인 시작 등 경계에서 이전 작업을 무효화한다. 각 비동기 작업은 시작 시 식별자를 보관한다. 토큰 저장·삭제와 UI 상태 변경은 현재 식별자와 일치할 때만 적용한다.
2. 검사와 토큰 저장 사이에 로그아웃이 끼어들 수 없도록 검증·저장·폐기를 같은 동기화 규칙으로 처리한다. 저장 계층과 화면 상태 계층이 각자 다른 기준을 쓰지 않게 한다. `Job.cancel()`만으로 늦은 콜백의 적용을 막았다고 판단하지 않는다.
3. bootstrap 오류를 구분한다. 오프라인·timeout·5xx·일시적 요청 제한은 저장 토큰을 유지하고 연결 재시도 화면을 제공한다. refresh로도 확정된 인증 무효·회원 이용 중지 등은 해당 현재 세션을 폐기한다. 이전 세션에서 발생한 오류는 새 세션을 폐기하지 않는다.
4. 오프라인에서는 이전 사용자 정보만으로 승인된 서비스 접근을 새로 확정하지 않는다. 토큰을 보존한 미검증 상태에서 재시도하고, 연결 복원 후 `/auth/me`로 회원·승인 상태를 확인한다.
5. ID/PW 및 소셜 로그인, 가입 완료, 최초 동문 인증 제출·재시도, refresh의 성공·실패 경로 모두 같은 적용 규칙을 사용한다. 일반 coroutine 취소는 오류 안내·세션 삭제로 바꾸지 않고 전파한다.
6. refresh는 기존 single-flight 및 회전 토큰 저장 보장을 유지한다. 이전 요청이 폐기되면 새 세션 저장소에 회전 결과를 쓰지 않는다. 새 세션이 이전 refresh 작업을 공유하거나 이전 실패의 영향을 받지 않게 한다.
7. 로그아웃은 로컬 무효화를 즉시 수행하고 서버 세션 폐기는 요청 시작 시 캡처한 세션으로 실행한다. 이전 로그아웃의 지연 응답이 새 로그인을 지우지 않게 한다. 취소 후 서버에서 이미 발급된 늦은 로그인 응답은 클라이언트에 저장하지 않으며, 가능하면 그 응답의 SID만 정리한다. 전역 로그아웃으로 다른 정상 세션을 폐기하지 않는다.
8. 회원 생성 뒤 인증 신청만 실패한 경우와 회원 생성 전 취소를 구분한다. 전자는 기존 설계대로 제한된 재시도 세션을 유지한다. 취소가 이미 서버에 commit된 회원 생성을 자동으로 되돌린다고 안내하지 않는다. 다음 공급자 로그인으로 복구할 수 있게 한다.

| --- | --- |

## 4. 작업 2 — backend 소셜 재연결

대상: `auth_repo.go`, `account_connections_repo.go`, `auth_account_connections.go`, 연결 API 오류 매핑 및 provider revocation 작업.

### 변경 내용

- 공급자 재인증과 현재 서비스 계정 인증을 전제로, 동일 회원의 `REVOKED` identity를 잠금·조건부 갱신으로 재활성화한다. `REVOKED_AT`를 해제하고 검증 시각과 새로운 공급자 자격정보를 갱신한다.
- `ACTIVE`이고 동일 회원이면 중복 요청을 성공으로 처리한다. 다른 회원의 `ACTIVE` identity는 409 충돌로 거절한다. 유일성 제약은 유지한다.
- legacy 연결·canonical identity·암호화 공급자 자격정보를 한 트랜잭션으로 맞춘다. 실패 시 일부 연결만 남지 않게 한다. 기존 native ID/PW·프로필·phone claim을 변경하지 않는다.
- 이전 DISCONNECT outbox의 지연 재시도가 새 연결을 해제하지 않게 연결 세대 또는 자격정보 버전과 작업 대상을 대조한다. 새 연결 완료 뒤 오래된 worker가 provider 요청이나 최종 DB 삭제를 수행하는 경계도 검수한다.
- 원인을 확인할 수 있는 비민감 오류 코드와 충돌/재시도 안내를 제공한다. raw provider subject·토큰을 오류 로그에 넣지 않는다.

첫 수정에서는 **다른 회원에 속한 REVOKED identity를 자동 재할당하지 않는다.** 해당 경우의 계정 이동 정책은 별도 명시적 흐름으로 정의한다. 동일 회원 재연결 수정은 이 정책 결정과 분리해 진행한다. 이메일 일치만으로 소셜 계정을 연결하거나 계정을 병합하지 않는다.

### 필수 검증

실제 MariaDB에서 최초 연결 → 해제 → 동일 회원 재연결을 통과시킨다. 반복 해제/연결, 동일 요청 재전송, 두 회원의 동시 연결, 해제와 재연결 경합, 오래된 outbox 실행, 마지막 로그인 수단 보호 및 credential 저장 실패 rollback을 추가한다. Apple도 공통 repository 경로를 합성 fixture로 검증한다.

실기기에서는 native 회원에 Kakao 재연결 → 로그아웃 → Kakao 로그인 → 동일 회원으로 진입을 확인한다. 이후 ID/PW 로그인과 회원 정보 보존도 확인한다. 이전 QA에서 차단된 native+Kakao 재로그인 경로를 여기서 완료한다.

## 5. 작업 3 — Android 카카오 취소 및 안내

### Kakao 취소: AUTH-QA-09

대상: `KakaoLoginAdapter.kt`, 로그인 및 프로필 연결 호출부.

현재 adapter는 `ClientErrorCause.Cancelled`를 처리하지만 실제 동의 취소는 웹 fallback으로 이어졌다. 따라서 먼저 설치 SDK 버전·앱 버전과 취소 콜백의 실제 오류 클래스/코드만 기록해 원인을 확인한다. `AuthError` 등 다른 유형이라고 미리 단정하지 않는다.

확인된 사용자 취소·동의 거절은 별도 결과로 정규화하고 웹 로그인으로 넘기지 않는다. Talk 미설치·사용 불가 등 fallback을 허용한 경우만 웹 경로를 사용한다. 정상 경로는 Talk 우선을 유지한다. 공식 예제도 `ClientErrorCause.Cancelled`인 사용자 취소에서 카카오계정 로그인을 이어서 호출하지 않는다. [Kakao Android 공식 문서](https://developers.kakao.com/docs/ko/kakaologin/android)

callback이 취소된 continuation이나 이전 인증 작업을 다시 완료하지 않게 하고, 중복 callback도 한 번만 처리한다. 로그인 취소는 signed-out으로, 로그인된 상태의 연결 취소는 기존 세션·미연결 상태로 복귀한다. 정상 취소에 일반 오류를 표시하지 않는다.

검수 조합: Talk 동의 하단 취소, 시스템 Back, 웹 로그인 취소, Talk 미설치/사용 불가, 정상 Talk 인증, 로그인 상태의 연결 취소, 취소 직후 재시도. 로그인·신규 가입·연결 화면에서 각각 실제 라우팅을 확인한다.

### 탈퇴 안내: AUTH-QA-13

대상: `AccountDeletionScreen.kt`.

최종 확인창을 실제 정책과 일치시키고, 접수증의 `canCancel` 및 자동 처리 시작 상태에 따라 취소 버튼과 안내를 표시한다. 단순 “언제나 취소 가능” 문구로 교체하지 않는다. 요청 전에는 처리 시작 전까지만 취소 가능하다고 설명하고, 처리 시작 후에는 취소 불가를 명확히 안내한다. 이미 확인한 실제 취소 기능은 회귀 검수한다.

## 6. 작업 4 — 탈퇴 미리보기와 완료 조건

대상: `account_erasure_preview*`, `account_erasure_database.go`, `account_erasure_identifiers.go`, `account_erasure_internal_verifier.go`, 휴대폰 인증 repository/소비 경로, `SessionCleanupJob`, 관리자 `AccountDeletionsPage.tsx`.

### 4-A. 단기 수정: 대기 원인과 예상 시각 표시

현재 SMS 인증 기록은 발급 후 24시간이 지난 행을 시간당 cleanup으로 정리한다. 이를 전체 탈퇴 완료를 지연시키는 알려진 잔류 대상으로 preview와 결과 상태에 표시한다. DB 처리 가능 여부와 전체 완료를 기다리는 항목을 구분한다. “DB 단계 보류 0건”이 “모든 저장소 즉시 완료”로 읽히지 않게 한다.

SMS 잔류 건수와 정책상 제거 예상 시각을 비민감 메타데이터로 제공한다. **발급 + 24시간 + 다음 hourly cleanup + worker 재검증**까지 고려한다. cleanup 실패 시 대기를 유지하고 담당자가 원인을 확인할 수 있게 한다. 전역 SMS 보관기간을 임의로 줄이거나 테이블을 완료 검증에서 통째로 제외하지 않는다.

### 4-B. 소유권 기반 검증과 삭제 계획

현재 문자열 검색은 동일 전화번호로 재가입한 새 회원까지 잡을 수 있다. 새 회원·인증 시도의 소유 관계와 오래된 삭제 대상 잔류를 구분한다.

- 신규 SMS grant의 소비 시 회원/인증 시도와 연결 관계를 기록한다. 스키마 확장이 필요하면 nullable 연관키·인덱스와 호환 가능한 migration을 설계한다. 회원 삭제 뒤에도 필요한 삭제 증거를 추적할 수 있는 방식으로 참조를 설계한다.
- 삭제 계획은 대상 회원에 귀속된 행과 요청 시 확보한 소유 증거를 기준으로 만든다. 삭제 시각 이후의 새 가입·SMS 요청은 이전 삭제 작업의 대상이 아니다.
- 기존의 소유권 불명확한 SMS 행은 전화번호 일치나 생성 시각만으로 강제 삭제하지 않는다. 기존 TTL 정리 대상으로 남기고 그 대기를 표시한다.
- 새 회원의 현재 identity/phone claim처럼 소유권이 증명된 정상 기록은 이전 회원의 잔류 증거와 구분한다. 전체 테이블 제외 대신 행 단위로 판정한다. 소유권이 불명확한 자유 텍스트 잔류는 계속 조사 대상으로 둔다.
- preview·실행·완료 검증이 동일한 분류를 사용한다. 검토 후 대상 기록이 달라지면 기존 승인 fingerprint를 무효화한다. `database_erased` 상태의 기존 요청도 worker 재시도로 완료 검증을 이어갈 수 있게 한다.

필수 테스트는 오래된 회원 삭제 → 같은 전화번호 새 가입 → 새 grant 소비 → 이전 worker 재시도다. 새 회원/claim/grant가 유지되고, 이전 회원의 잔류가 제거된 뒤 이전 요청은 완료돼야 한다. SMS 잔류 자체와 새 회원 문자열 충돌을 **각각 단독 fixture**로 재현해 영향도 분리한다.

fake clock으로 24시간 경계, hourly cleanup 지연·실패·재시도, 만료 전 유효 grant 보호, 소유권 불명확한 기존 행, 동시 가입/삭제 및 preview 변경을 검증한다. 마지막에 요청 15·16의 실제 상태를 다시 읽어 확인하되, 수동 완료 증거를 만들어 강제로 종료하지 않는다.

## 7. 작업 5 — 구독 참조 보류 처리

AUTH-QA-10은 공통 서버의 구독 처리 공백이다. iOS 담당자의 현재 작업과 맞춰 범위를 정하며 원본 iPhone 계정의 운영 기록은 이번 계획 작성에서 조작하지 않는다.

`failed`/`pending` 명칭이나 청구키 부재만으로 삭제 가능하다고 판단하지 않는다. 결제 상태와 외부 처리 가능성을 확인하고, 종료가 확인된 구독 참조를 정리하는 공식 관리자/worker 경로를 만든다. 근거·처리자·대상을 기록하고 반복 실행이 안전하도록 한다. 실제 진행 중 결제, 활성 청구키, 확인되지 않은 pending은 기존 보류를 유지한다.

preview와 worker가 같은 판단을 사용하도록 하고, 새 참조가 생기면 이전 승인을 거절한다. 검증된 실패·취소, 미확정 pending, 활성 구독, 공급자 조회 실패를 합성 MariaDB/API 테스트로 구분한다. 기부 증빙·파일·제3자 기록의 정당한 보존은 별도로 유지한다.

## 9. PR 분할과 검증·적용

권장 PR은 Android 세션/오프라인 처리, backend 소셜 재연결, Android SDK 취소/탈퇴 안내, backend·관리자 탈퇴 분류/소유권, 구독 정리의 5개다. 스키마 확장이 생기면 호환 migration과 소비 경로 변경을 분리해 적용 순서를 명시한다. iOS는 별도 담당 PR로 인계한다.

각 PR에 포함할 것은 결함 ID, 수정 전/후 동작, 회귀 테스트, 상태·데이터 호환성, 알려진 미검수 경계다. 회귀 테스트를 먼저 실패시키고 수정 후 통과시킨다. 상태 머신·거래 경계를 검수하는 테스트를 우선하며 단순 문구 변경을 위해 구현을 복제한 테스트를 추가하지 않는다.

적용 순서는 스키마의 호환 확장 → backend/관리자 → 수정 Android 앱 → 실제 계정 흐름 검수다. 단일 담당자가 Android 기기를 사용하고 관리자에서는 QA 회원만 승인·처리한다. root `jerryhwang018`은 유지하고 iOS 계정은 해당 담당자가 관리한다.

운영 적용 전에는 실제 배포 구조와 테스트 결과로 배포·롤백 절차를 구체화한다. 서버/API는 이전 앱과 호환성을 유지하고 migration은 additive 변경을 우선한다. 소유권 기록이 시작된 뒤 과거 바이너리로 되돌릴 때 기록 손실이나 완료 검증 누락이 생기지 않는지 확인한다. 수정되지 않은 앱 바이너리가 남아 있으면 플랫폼 검수 완료로 표시하지 않는다.

관측 항목은 오프라인 후 토큰 삭제, 오래된 응답 무시, 연결 충돌/재연결 성공, 탈퇴 stage별 체류 시간 및 SMS cleanup/간접 식별값 잔류다. 비밀번호·OTP·access/refresh·provider subject·연락처를 관측 로그에 기록하지 않는다.

## 10. 출시 검수 완료 조건

- Android AUTH-QA-01–05·09·13 및 공통 서버 11·12 회귀 테스트가 통과한다. 실기기 결함은 수정 앱에서 다시 검수한다.
- 기본 단위 테스트, 실제 MariaDB 인증 Golden/추가 edge 테스트, 현재 UI에 맞춘 관련 E2E가 통과한다. 기존 migration manifest 실패는 별도 해결·근거 없이 전체 통과로 처리하지 않는다.
- ID/PW·Kakao 각각 신규 가입 → 대기 → 반려/재신청/승인 → 로그인 → 자동 로그인 → 로그아웃 → 탈퇴 → 로그인 차단을 검수한다. native 계정의 Kakao 연결 → 해제 → 재연결 → Kakao/ID-PW 재로그인도 포함한다.
- 회원 생성 전 실패·취소에는 서비스 세션이 없고, 회원 생성 후 인증 신청 실패는 제한된 재시도 세션만 유지된다. 오래된 응답은 새 로그인이나 로그아웃 결과를 변경하지 않는다.
- 탈퇴 preview와 실제 처리 결과가 일치하며, 보존/대기 대상이 없어진 뒤 전체 완료에 도달한다. 같은 전화번호로 재가입한 새 계정은 유지된다. 요청 15·16은 실제 완료 상태와 잔류 검증을 따로 확인한다.
- 구독 참조 문제의 후속 완료와 iOS 02–04·06–08 및 신규 가입 검수 결과는 해당 담당자의 증거로 확인한다. 완료되지 않으면 전체 Android+iOS 인증 검수는 계속 미완료다.

작업 1–5의 구현·자동 검증을 완료했다. Android 실기기에서 수정 앱을 검수하고, 기존 migration 승인 계약을 정합화한 뒤 additive schema와 backend/관리자 변경을 운영에 적용해야 한다. iOS 수정·검수는 별도 담당 범위다.
